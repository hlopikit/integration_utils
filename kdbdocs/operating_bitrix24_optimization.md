# OPERATING в Bitrix24: сигнал к разбору и оптимизации вызовов

Статус: готово к синхронизации

## Назначение

`OPERATING` (в логах проекта — событие `method_operating`) означает, что вызов REST API Bitrix24 получил заметное значение `time.operating`. Это не самостоятельная прикладная ошибка и не основание просто увеличить таймаут. Для проекта это сигнал изучить логику конкретного сценария и сократить либо оптимизировать обращения к API.

Правило согласовано для проектов: при появлении `OPERATING` нужно найти конкретный сценарий, понять причину дорогого вызова и подтвердить улучшение измерениями.

## Где находится обработка

Общий механизм расположен в `integration_utils` и используется разными приложениями проекта.

- Одиночные REST-вызовы: `integration_utils/bitrix24/functions/api_call.py`, функция `api_call()`.
- Пакетные REST-вызовы: `integration_utils/bitrix24/functions/batch_api_call.py`, функция `_batch_api_call()`.
- Публичные обертки токена: `integration_utils/bitrix24/bitrix_token.py` и `integration_utils/bitrix24/models/bitrix_user_token.py`.

Для одиночного вызова `api_call()` читает `time.operating` из JSON-ответа. При значении больше `300` записывается `method_operating`; начиная с `400` запись имеет уровень warning, ниже — info.

Для `batch` `_batch_api_call()` берет максимум из `result.result_time[*].operating` и верхнеуровневого `time.operating`. После записи события код делает паузу `operating - 300`; пауза снижает риск последующих ограничений, но не устраняет причину медленного сценария.

## Что делать при появлении OPERATING

1. Зафиксировать контекст записи: время, портал, имя одиночного метода или перечень методов `batch`, tag логгера и вызывающий cron/action/view.
2. Открыть место вызова и восстановить бизнес-сценарий: какая сущность обрабатывается, за какой период, сколько записей и почему именно эти методы вызываются.
3. Посчитать обращения к API в рамках одного запуска. Отдельно проверить повторные запросы одних и тех же сущностей, N+1-паттерн, лишнюю пагинацию и получение неиспользуемых полей.
4. Проверить, нельзя ли ограничить выборку фильтром, периодом или `select`; получить данные одним пакетным вызовом; переиспользовать уже загруженные данные в пределах операции; перенести независимые запросы в `batch`.
5. После изменения сравнить фактический результат сценария до и после: данные не потеряны, число запросов уменьшилось, а `time.operating` и повторение `method_operating` снизились или исчезли.

## Типовые причины и меры

| Наблюдение | Что проверить | Предпочтительное улучшение |
| --- | --- | --- |
| Один и тот же метод вызывается для каждой записи | Цикл по сделкам, пользователям, задачам или файлам | Загрузить данные набором, сгруппировать обращения, использовать `batch` для независимых методов |
| Возвращается слишком большой набор данных | Фильтры, период, поля ответа, пагинация | Добавить точные фильтры и `select`, разбить обработку на осмысленные порции |
| Повторно читается уже известная сущность | Вызовы helper-ов внутри вложенных циклов | Передать объект/словарь вниз по цепочке или использовать кэш только в границах текущей операции |
| Дорогой `batch` содержит разнородную работу | Список команд, число команд, связь с результатами | Исключить дубли, отделить необязательные вызовы, сформировать меньшие независимые пакеты |
| Проблема возникает в cron | Частота запуска, пересечение запусков, объем исторических данных | Обрабатывать только новые или измененные записи, хранить корректный курсор и не пересчитывать неизменившуюся историю |

## Что не считать решением

- Увеличение таймаута без анализа вызовов: это позволяет дольше ждать, но не уменьшает нагрузку.
- Пауза после `batch`: это защитная реакция существующего клиента, а не оптимизация бизнес-логики.
- Отключение лога `method_operating`: оно скрывает диагностический сигнал.
- Бездумное кэширование между запусками: оно может вернуть устаревшие данные. Межзапусковый кэш допустим только с определенными правилами актуальности и инвалидирования.

## Проверка результата

Для каждой оптимизации нужно сохранить в задаче или отчете:

- сценарий и конкретный метод либо пакет методов, вызвавший `OPERATING`;
- исходную причину: количество вызовов, объем выборки, повторный вызов или другой подтвержденный факт;
- что изменено в алгоритме;
- проверку корректности результата на репрезентативных данных;
- сравнение числа запросов и значений `time.operating` до и после, если такие данные доступны.

Если `OPERATING` остается после устранения очевидных повторов, следующий шаг — разбирать конкретный метод Bitrix24, его параметры, объем данных и ограничения портала. Не следует объявлять оптимизацию успешной только потому, что запрос завершился без HTTP-ошибки.
