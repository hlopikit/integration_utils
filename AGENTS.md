# AGENTS.md

Инструкции для ИИ-агентов по работе с Bitrix24 REST API через `integration_utils`.

Файл описывает, какие объекты и helper-методы использовать в коде, как читать результаты API и каких типовых ошибок избегать.

## Токены

### `BitrixToken`

Легкий объект для прямого обращения к Bitrix24 REST API. Не является Django-моделью.

Что принимает:

- `domain` - домен портала без протокола;
- `auth_token` - OAuth access token;
- `web_hook_auth` - токен входящего вебхука.

Когда использовать:

- в скриптах и утилитах без ORM;
- при авторизации через входящий вебхук;
- когда не нужен доступ к связанным моделям пользователя, портала и приложения.

Пример:

```python
from integration_utils.bitrix24.bitrix_token import BitrixToken

token = BitrixToken(domain="example.bitrix24.ru", web_hook_auth="1/webhook_key")
response = token.call_api_method("user.current")
```

### `BitrixUserToken`

Django-модель OAuth-токена пользователя приложения. Используется в основном коде приложений.

Что умеет:

- хранит связь с пользователем, порталом и приложением;
- перед REST-вызовом обновляет токен через `refresh_if_needed`;
- при `expired_token` пробует обновить токен и повторить вызов;
- поддерживает те же call-методы, что и `BitrixToken`.

Когда использовать:

- в Django-коде приложения;
- когда запрос должен выполняться от имени конкретного пользователя;
- когда нужны данные портала, пользователя, приложения или проверка админских прав.

## Обращение к API

### `call_api_method`

Выполняет один REST-вызов.

Что принимает:

- `api_method` - имя REST-метода;
- `params` - параметры метода;
- `timeout` - timeout одного HTTP-запроса;
- `retry_settings` - настройки повторных попыток, если они нужны.

Что возвращает:

- сырой JSON-ответ Bitrix24;
- в успешном ответе обычно есть `result` и `time`;
- для списочных методов один вызов обычно возвращает до 50 элементов и поля пагинации.

Когда использовать:

- получить один объект по ID;
- создать, обновить или удалить один объект;
- вызвать служебный метод;
- получить первую страницу списочного метода.

Пример:

```python
response = but.call_api_method("crm.deal.get", params={"id": deal_id})
deal = response["result"]
```

### `batch_api_call`

Выполняет несколько REST-команд через Bitrix24 `batch`.

Что принимает:

- `methods` - список команд;
- `timeout` - timeout одного HTTP-запроса к Bitrix24;
- `chunk_size` - размер чанка, от 1 до 50;
- `halt` - останавливать ли выполнение подзапросов после ошибки;
- `retry_settings` - настройки повторных попыток, если они нужны.

Формат команд без своих ключей:

```python
batch = but.batch_api_call([
    ("user.current", {}),
    ("app.info", {}),
])

current_user = batch["data_0"]["result"]
app_info = batch["data_1"]["result"]
```

Формат команд со своими ключами:

```python
batch = but.batch_api_call([
    ("current_user", "user.current", {}),
    ("app", "app.info", {}),
])

current_user = batch["current_user"]["result"]
app_info = batch["app"]["result"]
```

Свои ключи нужны, когда дальше в коде результат надо доставать по понятному имени, а не по `data_0`, `data_1`.

Что возвращает:

- `BatchResultDict`;
- один плоский словарь по всем чанкам;
- у каждого ключа есть `result`, `error`, `time`, `total`, `next`.

Ошибки отдельных подзапросов проверяй через:

```python
if not batch.all_ok:
    ...

for key, error in batch.iter_errors():
    ...
```

Когда использовать:

- нужно выполнить несколько независимых REST-команд;
- нужно получить несколько разных объектов;
- нужно массово вызвать один метод по разным ID;
- нужно выполнить связанные команды через `$result`.

### Связанные команды в batch

Bitrix24 позволяет использовать результат предыдущего подзапроса через `$result[ключ][поле]`.

```python
batch = but.batch_api_call([
    ("deal", "crm.deal.get", {"id": deal_id}),
    ("contact", "crm.contact.get", {"id": "$result[deal][CONTACT_ID]"}),
])
```

Используй связанные команды, когда всю цепочку можно считать одной бизнес-операцией. Если частичное выполнение может создать неконсистентность, раздели операцию и обработай результат явно.

`halt=0` продолжает выполнять подзапросы после ошибки и кладет ошибки в `result_error`. `halt=1` останавливает выполнение следующих подзапросов в batch после ошибки.

Не вкладывай `batch` внутрь `batch`: Bitrix24 REST это запрещает.

### `call_list_method`

Получает список по REST-методу с пагинацией.

Что принимает:

- `method` - списочный REST-метод;
- `fields` - параметры метода: `filter`, `select`, `order` и другие;
- `limit` - максимальное количество элементов;
- `return_total` - вернуть полный `total` вместе с результатом;
- `allowable_error` - допустимое расхождение длины результата с `total`;
- `batch_size` - сколько страниц запрашивать в одном batch, от 1 до 50;
- `retry_settings` - настройки повторных попыток, если они нужны.

Что возвращает:

- список элементов;
- если `return_total=True`, возвращает `(result, {"total": total})`.

Когда использовать:

- нужно получить весь список;
- нужно получить первые `limit` элементов;
- не нужно вручную работать с `start`, `next`, `total`.

Пример:

```python
deals = but.call_list_method(
    "crm.deal.list",
    fields={"filter": {"CATEGORY_ID": 0}, "select": ["ID", "TITLE"]},
    limit=500,
)
```

### `call_list_fast`

Быстро читает большие списки через batch, `start=-1` и фильтрацию по ID.

Что принимает:

- `method` - списочный REST-метод;
- `params` - параметры метода;
- `descending` - направление сортировки;
- `limit` - максимальное количество элементов;
- `batch_size` - размер batch, от 1 до 50;
- `retry_settings` - настройки повторных попыток, если они нужны.

Что возвращает:

- генератор элементов;
- если нужен список, явно оберни в `list(...)`.

Когда использовать:

- нужно быстро получить много элементов;
- метод есть в `METHOD_TO_ORDER`, `METHOD_TO_FILTER`, `METHOD_TO_ID`;
- метод поддерживает сортировку и фильтр по ID.

Когда не использовать:

- метод не описан в справочниках `call_list_fast`;
- метод игнорирует фильтр по ID;
- нужен универсальный способ чтения списка.

Пример:

```python
for deal in but.call_list_fast("crm.deal.list", params={"select": ["ID", "TITLE"]}):
    ...
```

## Нюансы списочных методов

Списочный REST-метод возвращает часть списка и признаки пагинации, обычно `total` и `next`. Один вызов обычно возвращает до 50 элементов.

Если нужен полный список, не пиши ручной цикл по `start`, если подходит `call_list_method`.

Через batch можно запросить до 50 страниц по 50 элементов, то есть до 2500 элементов за один HTTP-запрос к `batch`. Это уменьшает количество HTTP-запросов, но не отменяет лимиты ресурсоемкости методов.

## RetrySettings

`retry_settings` задает повторные попытки REST-вызова.

Пример:

```python
response = but.call_api_method(
    "crm.deal.get",
    params={"id": deal_id},
    retry_settings=but.RetrySettings(
        attempts=3,
        delay=1,
        exceptions=(BitrixApiException,),
        should_retry=lambda exc: exc.is_not_logic_error,
    ),
)
```

Правила:

- `attempts=3` означает максимум 3 вызова: первая попытка и до двух повторов;
- логические ошибки Bitrix24 не ретраить;
- для `BitrixApiException` проверяй `exc.is_not_logic_error`;
- write-методы ретраить только при идемпотентности или защите от дублей;
- retry для `batch_api_call` повторяет весь batch-вызов при исключении, а не отдельный подзапрос из batch.

## Лимиты Bitrix24

Bitrix24 ограничивает REST по времени выполнения запроса, интенсивности запросов и ресурсоемкости методов. Batch уменьшает число HTTP-запросов, но не отменяет лимиты вложенных методов.

При превышении интенсивности запросов Bitrix24 может вернуть `503 QUERY_LIMIT_EXCEEDED`. Если превышен лимит ресурсоемкости метода, возможен `429 OPERATION_TIME_LIMIT`; в ответах REST смотри `time.operating` и `time.operating_reset_at`.

## Ошибки

Не подавляй исключения REST API без явного бизнес-правила. Если обработка ошибки допустима, оставь в коде понятное условие, почему именно этот случай можно игнорировать или заменить дефолтным значением.

Если ошибка пришла внутри batch-подзапроса, проверяй `BatchResultDict`, а не только исключения Python.

Если у исключения уже есть смысловое свойство вроде `is_not_logic_error`, используй его вместо поиска по тексту ошибки.

## Что не делать

- Не писать ручную пагинацию, если подходит `call_list_method`.
- Не делать `call_api_method` в цикле, если запросы можно объединить через `batch_api_call`.
- Не использовать `call_list_fast` для метода, которого нет в его справочниках.
- Не кодировать параметры REST-запросов вручную перед передачей в helper.
- Не подменять ошибочный ответ API пустым значением без явного бизнес-правила.
