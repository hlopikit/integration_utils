# AGENTS.md

Инструкции для ИИ-агентов по работе с Bitrix24 REST API через `integration_utils`.

Файл описывает, какие объекты и helper-методы использовать в коде, как читать результаты API и каких типовых ошибок избегать.

## Токены

### `BitrixToken`

Объект для прямого обращения к Bitrix24 REST API по домену и токену.

Что принимает:

- `domain` - обязательный домен портала без протокола;
- `web_hook_auth` - токен входящего вебхука в формате `user_id/webhook_key`;
- `auth_token` - OAuth access token, если запрос выполняется не через вебхук.

Когда использовать:

- при авторизации через входящий вебхук;
- в скриптах и разовых утилитах;
- когда для запроса достаточно домена и токена.

Пример:

```python
from integration_utils.bitrix24.bitrix_token import BitrixToken

token = BitrixToken(domain="example.bitrix24.ru", web_hook_auth="1/webhook_key")
response = token.call_api_method("user.current")
```

### `BitrixUserToken`

OAuth-токен пользователя установленного приложения Bitrix24. Это основной вариант для кода приложений.

Что умеет:

- хранит access token, refresh token и срок действия токена;
- связан с пользователем, порталом и приложением;
- перед REST-вызовом обновляет токен через `refresh_if_needed`;
- при `expired_token` пробует обновить токен и повторить вызов;
- поддерживает те же call-методы, что и `BitrixToken`.

Когда использовать:

- при работе через установленное приложение Bitrix24;
- когда запрос должен выполняться от имени конкретного пользователя;
- когда нужен пользовательский или админский токен из БД;
- когда в логике нужны данные портала, пользователя, приложения или проверка админских прав.

## Обращение к API

### `call_api_method`

Выполняет один REST-вызов к указанному методу Bitrix24.

Что принимает:

- `api_method: str` - обязательное имя REST-метода, например `crm.deal.get`;
- `params: dict | None` - параметры REST-метода; если параметров нет, можно не передавать;
- `timeout: int | tuple | None` - таймаут одного HTTP-запроса в секундах;
- `retry_settings: RetryDecorator | None` - настройки повторных попыток, если они нужны.

Таймаут:

- в проекте по умолчанию используется `settings.BITRIX_RESTAPI_DEFAULT_TIMEOUT = (3.05, 10)`;
- первое число в tuple - таймаут соединения, второе - таймаут получения ответа;
- если настройка `BITRIX_RESTAPI_DEFAULT_TIMEOUT` не задана, `BaseBitrixToken` использует `10` секунд;
- низкоуровневый `api_call` сам по себе имеет таймаут по умолчанию `60` секунд;
- облачный Bitrix24 разрывает соединение, если портал не успел отдать ответ за 60 секунд.

Что возвращает:

- `dict` с ответом Bitrix24;
- успешный REST-ответ содержит `result`;
- в ответе Bitrix24 также приходит `time`;
- если REST-метод поддерживает пагинацию, один API-вызов возвращает не больше 50 элементов и поля пагинации `next` и `total`.

`time` в ответе Bitrix24:

- `start` - timestamp начала обработки запроса;
- `finish` - timestamp окончания обработки запроса;
- `duration` - длительность обработки запроса;
- `processing` - серверное время обработки;
- `date_start` - дата и время начала обработки;
- `date_finish` - дата и время окончания обработки;
- `operating_reset_at` - timestamp сброса счетчика operating;
- `operating` - расход лимита ресурсоемкости REST за запрос.

Когда использовать:

- получить один объект по ID;
- создать, обновить или удалить один объект;
- вызвать служебный метод;
- получить только первую страницу списочного метода.

Пример:

```python
response = but.call_api_method("crm.deal.get", params={"id": deal_id})
deal = response["result"]
```

### `batch_api_call`

Выполняет несколько REST-команд через Bitrix24 `batch`.

Что принимает:

- `methods: Sequence[tuple]` - обязательный список команд;
- `timeout: int | tuple | None` - таймаут одного HTTP-запроса к Bitrix24;
- `chunk_size: int` - размер чанка от 1 до 50, по умолчанию 50;
- `halt: int` - поведение batch при ошибке подзапроса;
- `log_prefix: str` - префикс для логов;
- `refresh: bool` - обновлять ли протухший токен;
- `retry_settings: RetryDecorator | None` - настройки повторных попыток, если они нужны.

`methods` принимает два формата команд:

- `(api_method, params)` - команда без своего ключа;
- `(key, api_method, params)` - команда со своим ключом.

`params` внутри команды - `dict` или `None`.

Формат команд без своих ключей:

```python
batch = but.batch_api_call([
    ("user.current", {}),
    ("app.info", {}),
])

current_user = batch["data_0"]["result"]
app_info = batch["data_1"]["result"]
```

Если ключ не передан, helper назначает ключи `data_0`, `data_1`, `data_2` по порядку.

Формат команд со своими ключами:

```python
batch = but.batch_api_call([
    ("current_user", "user.current", {}),
    ("app", "app.info", {}),
])

current_user = batch["current_user"]["result"]
app_info = batch["app"]["result"]
```

Свои ключи нужны, когда дальше в коде результат надо доставать по понятному имени, а не по `data_0`, `data_1`.

Как работает:

- один запрос Bitrix24 `batch` принимает максимум 50 команд;
- helper режет `methods` на чанки по `chunk_size`;
- если команд больше `chunk_size`, helper отправляет несколько HTTP-запросов к `batch`;
- при `chunk_size=50` список из 120 команд будет отправлен как 3 HTTP-запроса: 50, 50 и 20 команд;
- дублирующиеся ключи команд запрещены и приводят к `ValueError`;
- `batch` нельзя вкладывать в `batch`.

`halt`:

- `halt=0` продолжает выполнять подзапросы после ошибки и кладет ошибки в `result_error`;
- `halt=1` останавливает выполнение следующих подзапросов внутри текущего batch после первой ошибки.

Что возвращает:

- `BatchResultDict`;
- один плоский словарь по всем чанкам;
- ключ результата совпадает со своим ключом команды или с автоматически созданным `data_N`;
- у каждого ключа есть `result`, `error`, `time`, `total`, `next`.

Проверка ошибок отдельных подзапросов:

```python
if not batch.all_ok:
    ...

for key, error in batch.iter_errors():
    ...
```

Когда использовать:

- нужно выполнить несколько независимых REST-команд;
- нужно получить несколько разных объектов;
- нужно массово вызвать один метод по разным ID;
- нужно выполнить связанные команды через `$result`.

### Связанные команды в batch

Bitrix24 выполняет команды в batch последовательно. Результат предыдущего подзапроса можно использовать в следующем через `$result[ключ][поле]`.

```python
batch = but.batch_api_call([
    ("deal", "crm.deal.get", {"id": deal_id}),
    ("contact", "crm.contact.get", {"id": "$result[deal][CONTACT_ID]"}),
])
```

Используй связанные команды, когда всю цепочку можно считать одной бизнес-операцией. Например, если нужно прочитать одну сущность и сразу обновить другую по данным из первого ответа, один batch лучше двух отдельных REST-запросов.

Не объединяй команды в один batch, если частичное выполнение может создать неконсистентность, которую код дальше не обработает явно.

### `call_list_method`

Получает список по REST-методу, который поддерживает стандартную пагинацию Bitrix24.

Что принимает:

- `method: str` - обязательный списочный REST-метод;
- `fields: dict | list | None` - параметры метода: `filter`, `select`, `order` и другие;
- `limit: int | None` - максимальное количество элементов, которое нужно вернуть;
- `return_total: bool` - вернуть полный `total` вместе с результатом;
- `allowable_error: int | None` - допустимое расхождение длины результата с `total`;
- `timeout: int | tuple | None` - таймаут каждого HTTP-запроса к Bitrix24;
- `batch_size: int` - сколько страниц запрашивать в одном batch, от 1 до 50;
- `retry_settings: RetryDecorator | None` - настройки повторных попыток, если они нужны.

Что возвращает:

- `list` элементов;
- если `return_total=True`, возвращает `(result, {"total": total})`.

Как работает:

- первый запрос выполняется через `call_api_method`;
- если в ответе есть `next` и нужно получить еще страницы, следующие страницы запрашиваются через `batch_api_call`;
- `limit` ограничивает итоговое количество элементов.

Когда использовать:

- нужно получить весь список;
- нужно получить первые `limit` элементов;
- метод поддерживает стандартные `start`, `next`, `total`;
- не нужно вручную работать с пагинацией.

Пример:

```python
deals = but.call_list_method(
    "crm.deal.list",
    fields={"filter": {"CATEGORY_ID": 0}, "select": ["ID", "TITLE"]},
    limit=500,
)
```

### `call_list_fast`

Быстро читает большие списки через batch, `start=-1`, сортировку и фильтрацию по ID.

Что принимает:

- `method: str` - обязательный списочный REST-метод;
- `params: dict | None` - параметры метода;
- `descending: bool` - направление обхода по ID;
- `timeout: int | tuple | None` - таймаут каждого HTTP-запроса к Bitrix24;
- `limit: int | None` - максимальное количество элементов;
- `batch_size: int` - размер batch от 1 до 50;
- `retry_settings: RetryDecorator | None` - настройки повторных попыток, если они нужны.

Что возвращает:

- генератор элементов;
- если нужен список, явно оберни в `list(...)`.

Когда использовать:

- нужно быстро получить много элементов;
- не нужно хранить все полученные данные в памяти;
- достаточно один раз проитерироваться по результатам;
- метод есть в `METHOD_TO_ORDER`, `METHOD_TO_FILTER`, `METHOD_TO_ID`;
- метод поддерживает сортировку и фильтр по ID.

Когда не использовать:

- метод не описан в справочниках `call_list_fast`;
- метод игнорирует фильтр по ID;
- нужен универсальный способ чтения списка.

Пример:

```python
for deal in but.call_list_fast("crm.deal.list", params={"select": ["ID", "TITLE"]}):
    ...
```

## Нюансы списочных методов

Списочный REST-метод - это метод, который возвращает не один объект, а страницу списка объектов и поддерживает пагинацию через `start`.

Если API-метод поддерживает пагинацию:

- один REST-вызов возвращает не больше 50 элементов;
- в ответе возвращаются `next` и `total`;
- если `next` есть, следующую страницу можно запросить со `start=next`.

Если нужен полный список, используй `call_list_method`, когда метод поддерживает стандартную пагинацию.

Через один HTTP-запрос к `batch` можно запросить до 50 страниц по 50 элементов, то есть до 2500 элементов одной сущности. Это уменьшает количество HTTP-запросов, но не отменяет лимиты самого Bitrix24.

Не передавай в фильтр большое количество допустимых значений. Если значений больше 1000, такой фильтр нужно дробить на несколько запросов или выбирать другой способ получения данных. Исключение - фильтр только по ID: для него в `call_list_method` есть отдельная оптимизация.

## RetrySettings

`retry_settings` задает повторные попытки REST-вызова.

Пример:

```python
response = but.call_api_method(
    "crm.deal.get",
    params={"id": deal_id},
    retry_settings=but.RetrySettings(
        attempts=3,
        delay=1,
        exceptions=(BitrixApiException,),
        should_retry=lambda exc: exc.is_not_logic_error,
    ),
)
```

Правила:

- `attempts=3` означает максимум 3 вызова метода: первый вызов и до двух повторов;
- логические ошибки Bitrix24 не ретраить;
- для `BitrixApiException` проверяй `exc.is_not_logic_error`;
- write-методы ретраить только при идемпотентности или защите от дублей;
- retry для `batch_api_call` повторяет весь batch-вызов при исключении, а не отдельный подзапрос из batch.

## Лимиты Bitrix24

Bitrix24 ограничивает REST по времени выполнения запроса, интенсивности запросов и ресурсоемкости методов. Batch уменьшает число HTTP-запросов, но не отменяет лимиты вложенных методов.

Что важно учитывать:

- облачный портал разрывает соединение, если ответ не сформирован за 60 секунд;
- `timeout` в helper-методах применяется к каждому HTTP-запросу, а не ко всей бизнес-операции;
- если helper делает несколько batch-чанков, общий runtime может быть больше одного `timeout`;
- в ответах REST смотри `time.operating` и `time.operating_reset_at`;
- `503 QUERY_LIMIT_EXCEEDED` и `429 OPERATION_TIME_LIMIT` означают, что код уперся в лимиты Bitrix24.

## Ошибки

Базовый класс ошибок API - `BitrixApiException` из `integration_utils.bitrix24.exceptions`.

`call_api_method` при REST-ошибке выбрасывает исключение, а не возвращает успешный `dict`.

Основные случаи:

- `BitrixApiError` - Bitrix24 вернул JSON-ответ с ошибкой;
- `BitrixApiServerError` - сервер вернул невалидный ответ или ошибку без нормального JSON;
- `BitrixApiErrorNotFound` - частный случай `BitrixApiError` для ошибки `Not found`;
- `ExpiredToken` - токен протух; `BitrixUserToken` сам пробует обновить токен и повторить вызов;
- `BitrixTokenRefreshError` - не удалось обновить OAuth-токен;
- `SnapiError` - ошибка вызова Snapi-метода;
- `BitrixRequestException` - `requests.RequestException` при запросе к порталу;
- `BitrixOauthRefreshRequestException` - `requests.RequestException` при обновлении OAuth-токена;
- `BitrixConnectionError` - не удалось подключиться к порталу;
- `BitrixOauthRefreshConnectionError` - не удалось подключиться к серверу авторизации при обновлении OAuth-токена;
- `BitrixTimeout` - портал не ответил за переданный `timeout`;
- `BitrixOauthRefreshTimeout` - сервер авторизации не ответил за переданный `timeout` при обновлении OAuth-токена;
- `BatchApiCallError` - ошибка самого REST-вызова `batch`;
- `JsonDecodeBatchFailed` - batch вернул не JSON.

Промежуточные базовые классы:

- `BatchFailed` - базовый класс ошибок batch;
- `BaseRequestException` - базовый класс ошибок `requests`;
- `BaseConnectionError` - базовый класс ошибок соединения;
- `BaseTimeout` - базовый класс таймаутов.

Алиасы для обратной совместимости:

- `ConnectionToBitrixError = BitrixConnectionError`;
- `BitrixOauthConnectionError = BitrixOauthRefreshConnectionError`.

Что использовать в обработке:

- `exc.error` - код ошибки Bitrix24, если он есть;
- `exc.error_description` - техническое описание ошибки Bitrix24, если оно есть;
- `exc.status_code` - HTTP-статус, если он известен;
- `exc.friendly_error` - текст, который можно показать пользователю;
- `exc.is_not_logic_error` - признак инфраструктурной/временной ошибки, которую можно рассматривать для retry или warning-лога.

Для `BitrixApiError` используй смысловые свойства исключения вместо поиска по тексту ошибки.

Ошибки отдельных команд внутри `batch_api_call` нужно проверять через `BatchResultDict`:

- `batch.all_ok`;
- `batch.errors`;
- `batch.iter_errors()`.

Важно: ошибка отдельной команды в batch лежит в `BatchResultDict` и не равна Python-исключению. Исключение возникает, когда сломался сам запрос `batch`: невалидный JSON, общий `error` в ответе batch, истекший токен, timeout или ошибка соединения.

Не заменяй ошибочный ответ API пустым списком, пустым словарем или `None` без явного бизнес-правила. Если такой сценарий допустим, в коде должно быть понятно, почему именно эту ошибку можно обработать как пустой результат.

## Что не делать

- Не писать ручную пагинацию, если подходит `call_list_method`.
- Не использовать `call_api_method` по отдельности или в цикле, если запросы можно объединить через `batch_api_call`.
- Не использовать `call_list_fast` для метода, которого нет в его справочниках.
- Не кодировать параметры REST-запросов вручную перед передачей в helper.
- Не игнорировать ошибки подзапросов после `batch_api_call`.
