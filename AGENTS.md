# AGENTS.md

Инструкции для ИИ-агентов, работающих с `integration_utils`.

## Обращение к Bitrix24 API

- Для одиночного REST-вызова используй `BitrixUserToken.call_api_method(...)`.
- Для списочных методов используй `BitrixUserToken.call_list_method(...)` или `BitrixUserToken.call_list_fast(...)`, а не ручные циклы по `start`.
- Для пачки запросов используй `BitrixUserToken.batch_api_call(...)`.
- Не вызывай низкоуровневые `api_call`, `_batch_api_call` и функции из `integration_utils.bitrix24.functions.*` напрямую из бизнес-логики, если есть метод токена. Низкоуровневые функции нужны для внутренней реализации.
- Вызовы через `BitrixUserToken` важны, потому что модель токена сама обрабатывает refresh, `ExpiredToken` и совместимость с текущей авторизацией.
- Если в коде уже есть объект токена, не создавай новый `BitrixToken` вручную только ради REST-вызова. Используй имеющийся токен.
- Не передавай `auth` вручную в параметры REST-метода. Авторизация должна идти через токен.
- Не меняй домен портала вручную перед вызовом API. Домен должен браться из токена/портала, если задача явно не про исправление домена.

## Как выбрать метод

- `call_api_method` - один конкретный REST-запрос, например `crm.deal.get`, `user.current`, `im.message.add`.
- `call_list_method` - обычный способ получить весь список элементов REST-метода с постраничностью.
- `call_list_fast` - быстрый списочный запрос через `start=-1`, если метод поддерживается справочниками `METHOD_TO_*`.
- `batch_api_call` - набор независимых REST-команд, которые нужно отправить пачкой.
- Если метод возвращает список, сначала проверь, нет ли уже готовой поддержки в `call_list_method` / `call_list_fast`.
- Не собирай batch вручную строками, если рядом уже есть helper для нужного сценария.

## RetrySettings

- Для повторных попыток используй `RetrySettings` через токен:

```python
result = but.call_api_method(
    "crm.deal.get",
    params={"id": 1},
    retry_settings=but.RetrySettings(
        attempts=3,
        delay=1,
        exceptions=(BitrixApiException,),
        should_retry=lambda exc: exc.is_not_logic_error,
    ),
)
```

- `attempts` - общее количество попыток, включая первую.
- `delay` - пауза между попытками в секундах.
- `exceptions` - классы исключений, для которых разрешены повторы.
- `should_retry` - дополнительная проверка ошибки. Если функция вернула `False`, повтор делать нельзя.
- По умолчанию не добавляй retry ко всем запросам. Используй его только там, где повтор действительно безопасен и полезен.
- Логические ошибки Битрикс24 ретраить не нужно. Для `BitrixApiException` обычно проверяй `exc.is_not_logic_error`.
- Не ретрай запросы, которые могут создать дубли, если нет идемпотентности или явной защиты от дублей.
- Для read-only запросов retry обычно безопаснее, чем для write-запросов.
- Если retry добавляется в списочный метод, он должен пробрасываться до `call_api_method` или `batch_api_call`, а не реализовываться отдельным циклом внутри списочного метода.
- Не оборачивай один и тот же вызов retry дважды. Если базовый метод уже принимает `retry_settings`, наследник должен только пробросить параметр в `super()`.

## Ошибки API

- Не скрывай `BitrixApiException`, если вызывающий код должен принять решение по конкретной ошибке.
- Для логирования выбирай уровень по смыслу ошибки: не логическая ошибка обычно `warning`, логическая ошибка обычно `error`, если текущий контекст не требует другого поведения.
- Не заменяй специфичную ошибку на общий `Exception`, если код выше может обработать ее точнее.
- Если ошибка должна быть понятна пользователю, используй friendly-текст ошибки, когда он есть.
- Не показывай пользователю сырые токены, auth-параметры, refresh token, client secret и другие секреты.
- При обработке `ExpiredToken` учитывай существующую refresh-логику токена. Не добавляй отдельный refresh в бизнес-код, если токен уже умеет это делать.

## Стиль изменений

- Держи правки минимальными и рядом с существующей архитектурой.
- Не добавляй новые абстракции, если параметр можно просто пробросить в уже существующий слой.
- Не переносись из `integration_utils` в `bitrix_utils` автоматически. Если изменение планируется для обоих пакетов, сначала сделай его так, чтобы его было легко повторить вручную.
- Не меняй публичное поведение ради красоты кода.
- Если рядом есть старый стиль type comments, можно использовать его. Если файл уже использует аннотации Python 3, добавляй обычные аннотации.
