# Безопасная диагностика транспорта Bitrix24

Доработка от 18.11.2026 поверх коммита `e5506219` по задаче [#334943](https://b24.it-solution.ru/company/personal/user/1/tasks/task/view/334943/).

## Что сохраняется

`bitrix_request` и `bitrix_response` для обычного REST и REST 3.0 содержат время, проверенный домен портала с портом, имя REST-метода, количество параметров, признак webhook, HTTP-статус и размер тела ответа. Контекст присутствует и в сообщении, и в `params`, чтобы он был виден в уведомлениях и доступен для фильтрации.

Сырые тела запросов и ответов, query string, userinfo и webhook-часть URL не включаются в сообщения или структурированные параметры этих логов. Отказ от тел нужен и для неизвестных полей: произвольный `result` или бизнес-параметр может содержать секрет под любым именем. В HTTP-запрос параметры, auth и webhook URL передаются в исходном виде; ответ клиенту не редактируется.

Повторы 503, междоменный redirect и отказ redirect сохраняют счётчик, задержку и домен с портом. Сравнение netloc и логика повторных вызовов сохранены, включая исправление передачи `timeout` из актуальной ветки. Ошибки JSON и диагностика batch не записывают ответ сервера или текст исключения. `method_operating` для batch сохраняет имена методов и число вызовов каждого в текущем пакете, без значений параметров.

## OAuth и исключения

Обновление OAuth пишет ID записи токена, статус, размер ответа, `error` и `error_description`. Для отказов используется общий тип события `refresh_token_error`; новый код ошибки виден в сообщении без изменения кода библиотеки. Секретные query-параметры refresh URL и выданные токены не логируются.

`BitrixApiError` сохраняет в `str`/`repr` HTTP-статус, `error` и `error_description` без списка разрешённых кодов. Исходные атрибуты исключения не меняются. Полные тела, `message`, токены и успешные результаты в строковое представление не включаются.

`BatchFailed` с причиной `Response` показывает HTTP-статус и поля ошибки из JSON. Если ответ не является JSON, сохраняется только статус. Для ошибок отдельных команд и `CallListException` сохраняются `error` и `error_description`; пользовательские ключи команд и успешные результаты исключаются. Сетевые исключения показывают класс причины. Цепочки низкоуровневых исключений requests/JSON скрываются, чтобы их кадры не раскрывали запросы и тела ответов.

Общая очистка секретов уже реализована в `its_utils.app_logger.utils.secret_redaction.SecretRedactor` и применяется `ItsLogger` до сохранения и отправки логов. Она скрывает значения полей `password`, `token`, `secret` и других имён учётных данных, известные копии секретов, Bearer/Basic, JWT, ключи известных провайдеров и webhook-пути. Также есть эвристика строк, похожих на токены; она не гарантирует распознавание произвольного пароля без контекста. Транспорт не дублирует этот фильтр. Поля ошибок передаются в логгер без отдельного цензурирования, а общий фильтр может скрыть обнаруженный внутри них секрет.

У существующих `sensitive_variables` перечислены конкретные переменные с credentials, параметрами запросов и разобранными ответами. При `DEBUG=False` остальные locals остаются доступны reporter: таймауты, счётчики, статусы и проверенный контекст в `log_params`. Django применяет список также к вложенным вызовам до следующего такого декоратора. Поэтому функции преобразования параметров и сборки ответа batch, содержащие сырые данные, скрывают все locals. Отдельной обёртки над Django reporter в транспорте нет.

Защита параметров распространяется на внешние `BaseBitrixToken.call_api_method_v3`, `BaseBitrixToken.batch_api_call`, их вложенные `_call_method` и переопределение `BitrixUserToken.batch_api_call`. Для REST 3.0 скрываются `self` и `params`, для batch — `self` и `methods`; остальные настройки вызова сохраняются в отчёте.

В списки включены производные блоки ответа `data_time`, `result_time` и `operating`, которые не нужны для диагностики ошибок и могут содержать произвольные данные при некорректном ответе сервера. Отдельное поле `error` не скрывается. Для redirect скрыты также `old_domain` и `new_domain`: полный `netloc` может включать userinfo. Проверенные адреса остаются в метаданных, а числовое время выполнения — в `method_operating`.

В batch скрыты накопленный `responses`, пользовательские ключи в `name`, `seen_keys` и `safe_methods`, а также `_` с закодированными параметрами последней команды. Сбой запроса не раскрывает их через locals.

После переименования функция `batch_api_call` сохраняет прежний импорт через алиас `_batch_api_call = batch_api_call`. Старые версии `bitrix_utils` могут работать с обновлённым `integration_utils` без одновременного обновления обоих сабмодулей.

В транспортных обработчиках с уровнем ERROR и при диагностике profile после OAuth refresh явно передаётся `exc_info=False`, чтобы логгер не сохранял сырой HTML-отчёт и текст исключения дополнительно к безопасному сообщению. Существующие суффиксы классов исключений в типах этих событий сохранены явно. Общего обхода traceback и объектов, класса `CredentialRedactor` и служебной передачи токенов ради логирования нет.

Существующие сохраненные логи не удаляются и не переписываются. Токены не ротируются, миграции не требуются. Настройки логирования других приложений, внешние HTTP-debuggers и произвольные логи вызывающего кода остаются отдельными источниками, которые нужно проверять самостоятельно.

## Проверки и исходники

`integration_utils.bitrix24.test_transport_logging.TransportLoggingTests` проверяет OAuth/webhook, REST 3.0, вложенные и неизвестные секретные поля, ответы и не-JSON, 503/redirect, сетевые traceback, batch и refresh с фиктивными credentials. Реальная сеть запрещена, рабочая БД не используется. Проверяется и отсутствие секретов во всех аргументах логгера, и сохранность фактического HTTP-payload/результата. Отдельная проверка Django reporter выполняется с `DEBUG=False`.

Исходники: `bitrix24/functions/api_call.py`, `functions/log_metadata.py`, `functions/batch_api_call.py`, `models/bitrix_user_token.py`, `bitrix_token.py`, `exceptions.py`. Приложение `b24webhook` дополнительно маскирует auth и credential-поля в собственном `B24WebhookRequestLog.response_preview`; это не транспортный лог `bitrix_response`.
