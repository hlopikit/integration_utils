# Безопасная диагностика транспорта Bitrix24

Локальное изменение от 14.11.2026 по задаче [#334943](https://b24.it-solution.ru/company/personal/user/1/tasks/task/view/334943/). До публикации сабмодуля и выкладки проекта это поведение локального кода.

## Что сохраняется

`bitrix_request` и `bitrix_response` для обычного REST и REST 3.0 содержат время, проверенный hostname портала, имя REST-метода, количество параметров, признак webhook, HTTP-статус и размер тела ответа. Это позволяет сопоставлять вызовы и оценивать результат без записи credentials.

Сырые тела запросов и ответов, query string, userinfo и webhook-часть URL не включаются в сообщения или структурированные параметры этих логов. Отказ от тел нужен и для неизвестных полей: произвольный `result` или бизнес-параметр может содержать секрет под любым именем. В HTTP-запрос параметры, auth и webhook URL передаются в исходном виде; ответ клиенту не редактируется.

Повторы 503, междоменный redirect и отказ redirect сохраняют только счетчик, задержку и hostname. Сравнение netloc, включая порт, и логика повторных вызовов сохранены. Ошибки JSON и диагностика batch не записывают ответ сервера или текст исключения. `method_operating` сохраняет значение operating и контекст метода/портала.

## OAuth и исключения

Обновление OAuth пишет ID записи токена, статус и размер ответа. Секретные query-параметры refresh URL и access/refresh tokens из ответа не логируются. Известные коды отказа сохраняются в типе события; неизвестное значение `error` преобразуется в суффикс `unknown`, чтобы сервер не мог вернуть секрет в имени события.

`str` и `repr` у `BitrixApiError`, `BatchFailed` и сетевых исключений не сериализуют token, response, message или URL requests. Исходные значения остаются в атрибутах для обработки результата; их нельзя выводить в общий лог вручную. Цепочка низкоуровневого исключения requests/JSON скрыта в отображаемом traceback. Транспортные функции, batch и OAuth-методы отмечены `sensitive_variables()` для маскировки локальных переменных Django exception reporter при `DEBUG=False`. В production требуется `DEBUG=False`; эта защита не заменяет настройки внешних access-логов.

Существующие сохраненные логи не удаляются и не переписываются. Токены не ротируются, миграции не требуются. Настройки логирования других приложений, внешние HTTP-debuggers и произвольные логи вызывающего кода остаются отдельными источниками, которые нужно проверять самостоятельно.

## Проверки и исходники

`integration_utils.bitrix24.test_transport_logging.TransportLoggingTests` проверяет OAuth/webhook, REST 3.0, вложенные и неизвестные секретные поля, ответы и не-JSON, 503/redirect, сетевые traceback, batch и refresh с фиктивными credentials. Реальная сеть запрещена, рабочая БД не используется. Проверяется и отсутствие секретов во всех аргументах логгера, и сохранность фактического HTTP-payload/результата. Отдельная проверка Django reporter выполняется с `DEBUG=False`.

Исходники: `bitrix24/functions/api_call.py`, `functions/_log_metadata.py`, `functions/batch_api_call.py`, `models/bitrix_user_token.py`, `bitrix_token.py`, `exceptions.py`. Приложение `b24webhook` дополнительно маскирует auth и credential-поля в собственном `B24WebhookRequestLog.response_preview`; это не транспортный лог `bitrix_response`.
